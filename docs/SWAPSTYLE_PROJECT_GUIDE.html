SwapStyle

A practical guide to the Clothing Exchange & Swap Marketplace: what it does, how the code is organized, how to run it, and how its demo data and swap workflow fit together.

Prepared from the current source code · 14 November 2026

At a glance

SwapStyle is a browser-based clothing barter marketplace prototype. A visitor can browse sample garments, inspect details, estimate barter values, create a swap request, negotiate in a chat-style screen, and review activity on a dashboard. A profile switcher makes it possible to try the experience as different seeded demo accounts.

Important scope: The current app is a frontend demo. Its sample users, listings, swaps, and messages are stored in the browser's localStorage. There is no API server, shared database, live geolocation service, or production login system in this project.

A typical demo flow is: choose a profile in the top-right switcher → browse an available garment → open its details → start a swap proposal → switch to the other demo profile → respond in Negotiation & Chat → complete the swap → check the dashboard or admin metrics.

The switcher changes the active demo identity; it is not an authentication or authorization mechanism. The admin screen is likewise part of the client-side prototype.

2. Technology and project structure

  • React 19 builds the interface as reusable components.
  • Vite 8 serves the app during development and creates the production bundle.
  • React Context shares the current user, items, swaps, messages, and marketplace actions between screens.
  • Browser localStorage persists demo state between reloads on the same browser and origin.
  • lucide-react provides icons; canvas-confetti adds a completion effect.
  • Oxlint runs the project's lint command.

3. Install, run, check, and build

Prerequisites

  • Node.js ^20.19.0 or >=22.12.0 (the Vite toolchain's supported range in the lockfile).
  • npm, installed with Node.js.
  • A modern browser. Some demo garment/profile images are remote URLs and require an internet connection to load.

On Windows PowerShell

Open PowerShell in the project folder (the folder containing package.json) and run:

npm install
npm run dev

Open the local URL Vite prints in the terminal, usually http://localhost:5173. Keep the terminal open while using the development server. Vite's hot module replacement reloads changes as files are saved.

4. How state and persistence work

MarketplaceProvider initializes state from localStorage where possible and otherwise uses seed data from mockData.js. React effects write the latest values back to the browser. The current storage keys are:

KeyStored data
swapstyle_current_userThe selected demo profile.
swapstyle_usersSeeded and additional demo users.
swapstyle_itemsSeeded and newly listed garments.
swapstyle_swapsSeeded and newly created swap requests and statuses.
swapstyle_messagesSeeded and sent chat messages.

On startup, seeded account information is refreshed from INITIAL_USERS while preserving additional stored accounts and the previously selected account ID. Saved listing and swap avatars are resolved against the refreshed users so an edited demo profile image appears in related UI.

Reset behavior: “Reset Demo Simulation” resets marketplace demo state and currently calls localStorage.clear(). This clears all localStorage entries for the current site origin, not only the SwapStyle keys. Use it only when you want a clean local demo.

Because localStorage belongs to a particular browser and origin, data is not synchronized to another device, browser profile, or person. Clearing site data or using the reset button removes the locally saved changes.

5. Barter value calculation

The valuation function is calculateSwapValue in src/context/MarketplaceContext.jsx. It uses the category base values, brand tiers, and condition multipliers exported from src/mockData.js. The values are estimates in Indian rupees (₹), not market quotes.

Without a retail price

base estimate = category base value × brand multiplier × condition multiplier

When an original retail price is provided

retail estimate = original retail price × 0.42 × condition multiplier
combined estimate = 0.40 × base estimate + 0.60 × retail estimate

The result is rounded to a whole rupee and has a minimum of ₹500. Unknown categories, brands, or conditions use the function's fallback values.

The calculator shows a fair-trade indicator when the value difference is at most ₹800 or the smaller estimate is at least 75% of the larger one. This is a demo rule; it does not guarantee that two people consider a swap fair.

7. Testing and troubleshooting

SymptomWhat to try
Updated sample profile details are not visibleReload the page and check the matching profile ID. The app refreshes seeded user fields on startup; user-generated local data is otherwise persisted.
A profile or garment picture is blankCheck the image URL by opening it directly and confirm the browser has internet access. Remote image hosts can return errors or block hotlinking.
App shows an older stateCheck the selected demo account and the current site's saved data. Reset the demo only if you intend to discard local changes.
Port 5173 is already in useStop the other Vite process or run npm run dev -- --port 5174, then open the URL Vite prints.
Dependency or Node compatibility errorUse a supported Node version, then run npm install in the project root.
Production build failsRead the first build error in the terminal, fix the referenced source issue, then rerun npm run build.

Recommended validation after a code change: run npm run lint, run npm run build, and manually exercise the screen or workflow that changed in the browser.

8. Current limitations and sensible next steps

  • No backend: records only exist in one browser's localStorage. For shared accounts and listings, add an API and persistent database.
  • No real authentication: the profile switcher is a demo convenience, not secure identity or authorization. Add server-verified authentication and role checks before exposing admin actions.
  • No real-time transport: chat messages are local state; multiple users do not receive live updates.
  • Mock proximity: listing distance and city are sample fields. The app does not request device location or calculate routes.
  • Demo metrics: environmental impact and listing data are illustrative UI figures, not verified impact accounting.
  • External images: profile and garment image availability depends on third-party hosts.
  • No automated test command: add focused tests as business rules and persistent data flows become more important.

For a production-ready version, build and test in small stages: define backend data models and APIs; implement authentication and authorization; migrate listings, users, swaps, and messages to the server; validate uploads and user input; add automated tests; then add operational logging, privacy controls, and deployment configuration.
